Abstract

The evaluation and tabulation of academic performance across modern autonomous engineering institutions requires precision, speed, strict adherence to institutional grading ordinances, and absolute data integrity. Traditional grading mechanisms that rely on manual ledger books or disconnected spreadsheet files frequently suffer from human calculation blunders, lack of role-based authorization, broken formula links, and severe delays in transcript publication.

To resolve these critical operational shortcomings, this project introduces Gradely (Acadex 2.0), a high-performance, responsive academic grade evaluation and student merit management platform designed specifically for autonomous Choice-Based Credit System (CBCS) engineering curriculums. Gradely provides a zero-dependency, client-side reactive architecture backed by synchronized local persistence, ensuring sub-millisecond execution with zero cloud server hosting overhead, while also supplying a complete full-stack reference architecture (Node.js, Express, Prisma ORM, and PostgreSQL) for multi-tier deployments.

The platform implements a strict 10-point institutional grading scale ($A^+$ through $F$), automated credit-weighted Semester Grade Point Average (SGPA) computation, instant rank allocation with secondary aggregate percentage tie-breaking, role-based access control (RBAC) across Administrator, Faculty, and Student tiers, client-side cryptographic PDF transcript issuance, CSV tabular exports with CSV formula injection protection, an institutional security mutation audit trail, and an adaptive Tri-State Theme Engine (Light, Dark, and System). Deployed to production on Render, the system has been verified with a 20-candidate demonstration cohort across 7 core first-year engineering disciplines, achieving 100% calculation accuracy and robust cross-platform accessibility.

Keywords: Choice-Based Credit System (CBCS), SGPA Calculation, Autonomous Grading Ordinance, Role-Based Access Control, Client-Side Cryptographic PDF Transcripts, Zero-Dependency Reactive Architecture, Dark Mode Theme Engine, Render Cloud Deployment.

Chapter 7: Introduction

Higher education institutions worldwide, particularly autonomous technological colleges and engineering universities, have adopted the Choice-Based Credit System (CBCS) under the guidance of statutory accreditation boards such as the National Board of Accreditation (NBA) and the All India Council for Technical Education (AICTE). Under this educational paradigm, student progress is evaluated through continuous and end-semester grading, where every academic course carries a designated credit weighting that directly influences the candidate's Semester Grade Point Average (SGPA) and Cumulative Grade Point Average (CGPA).

Despite the universal adoption of credit-weighted evaluation, the software infrastructure supporting academic record administration in many engineering departments remains fragmented. Faculty members frequently compute candidate grades in localized desktop spreadsheets or offline paper ledgers, which introduces severe risks of human error, transcription mistakes, data loss, and unauthorized grade alteration.

Gradely (Acadex 2.0) was conceptualized and engineered to address this gap. Built as a unified, client-reactive academic grading suite, Gradely automates the entire semester evaluation lifecycle: from student and curriculum registration to instant marks entry, credit-weighted SGPA calculation, tie-breaking rank allocation, cohort-wide performance analytics, and cryptographic PDF transcript generation.

Chapter 8: Problem Statement

The traditional academic evaluation workflow in engineering institutes exhibits multiple critical vulnerabilities:

  • Calculation Inaccuracies: Manual calculation of course percentages, grade point conversions, and credit-weighted averages is highly error-prone when managing cohorts of several hundred candidates across multiple courses.
  • Lack of Role-Based Authorization: Spreadsheets lack granular security. A teacher entering marks for one course can accidentally overwrite marks for another course, or students may gain illicit access to unfinalized grade registers.
  • Inconsistent Grading Ordinances: Universities periodically update minimum passing marks, grade brackets, or grace-mark regulations. Propagating these changes across disconnected spreadsheets is tedious and prone to version skew.
  • Sluggish Transcript Delivery: Generating official paper transcripts often takes weeks after examinations, creating administrative bottlenecks for students seeking internships or competitive exam verifications.
  • High Infrastructure Complexity: Traditional enterprise software requires expensive database servers, complicated backend runtimes, and dedicated system administrators, making it difficult for individual departments to deploy and maintain.

Chapter 9: Objectives of the Project

The primary technical and academic objectives of the Gradely project are:

  1. Autonomous CBCS Grading Engine: Develop a robust calculation engine that accurately maps percentage scores into a 10-point institutional scale ($A^+$ to $F$) and computes credit-weighted SGPA using strict mathematical summation:
    SGPA = Σ (Grade Point_i × Credit_i) / Σ Credit_i
  2. Dynamic Class Merit & Tie-Breaking Register: Implement an automated class rank algorithm that sorts candidates by SGPA, seamlessly resolving ties using total aggregate percentage.
  3. Zero-Dependency Client-Side Architecture: Deliver a self-contained web platform capable of running in any modern web browser without requiring heavy backend servers or complex database configurations, while maintaining synchronized local state persistence.
  4. Role-Based Access Control (RBAC): Provide dedicated interface views for Administrators (full governance, user creation, curriculum editing, audit logs), Faculty (scoped departmental cohort views and marks administration), and Students (read-only personal scorecard).
  5. Client-Side Cryptographic Document Generation: Enable one-click issuance of official institutional merit registers and certified student scorecards in PDF format directly inside the client's browser using jsPDF.
  6. Ergonomic & Responsive Experience: Incorporate a Tri-State Theme Switcher (Light, Dark, and System Default) and responsive layout patterns ensuring zero-overflow usability across smartphones, tablets, and desktop workstations.

Chapter 10: Scope of the Project

The functional scope of Gradely encompasses the complete examination administration for undergraduate and postgraduate university departments:

  • Curriculum Management: Administration of up to 50 active course papers per semester, covering theory papers, laboratory practicals, and engineering projects with custom credit weightings.
  • Cohort Administration: Handling cohorts from small departmental sections (20–60 candidates) to entire institutional semesters (1,000+ candidates).
  • Evaluation Lifecycle: Management of examination states through explicit publication controls (Draft / In Progress vs. Official Published Transcripts).
  • Institutional Audit Logging: Automatic timestamped recording of every administrative action (user additions, subject modifications, marks updates, publication status shifts).
  • Data Portability: Import and export of candidate directories and marks registers via CSV and official PDF formats with formula injection sanitization.

Chapter 11: Existing System

In most conventional academic setups, examination evaluation proceeds through manual or semi-automated methods. Faculty members enter candidate marks into local Microsoft Excel or Google Sheets files. Once compiled, these files are emailed to the controller of examinations, who manually merges columns, applies formula lookups, and typesets individual scorecards.

Key deficiencies of the existing system include:

  • No Input Boundary Checking: A teacher can mistakenly input -15 or 150 marks for a 100-mark paper without any validation warning.
  • Formula Corruption: A single misplaced parenthesis or corrupted cell reference in a spreadsheet formula invalidates the SGPAs of all downstream students.
  • Data Silos: Grade data remains locked on personal laptops, risking permanent data loss upon hardware failure.
  • Zero Audit Trail: It is impossible to identify who modified a specific mark or when a grade was changed after compilation.

Chapter 12: Proposed System

The proposed Gradely (Acadex 2.0) platform replaces disconnected workflows with a unified, browser-native academic portal. By enforcing client-side validation at the input boundary, marks cannot exceed the maximum course threshold or drop below zero. SGPAs and letter grades are computed in real-time as keystrokes occur, providing immediate feedback to faculty.

  • Publication Lifecycle Control: Toggle semester results between `Evaluation In Progress` (draft) and `Official Results Published`. When published, official transcripts receive institutional validation stamps.
  • Audit Trail: Chronological log capturing mutation timestamps, user roles, action types, and granular change descriptions.

The Faculty module is tailored for subject teachers and course coordinators:

  • Scoped Departmental Cohort: Teachers only see students enrolled in their assigned sections and departments (e.g., Prof. Alok Verma manages `CSE-A` and `CSE-B` for `CSE101` and `MTH101`).

Chapter 22: Storage Architecture & Data Flow

Data in Gradely is managed through a normalized JSON state structure synchronized with browser storage. The schema ensures zero redundancy: student objects contain only enrollment attributes and an array of raw marks (k), while all calculations (percentages, grades, credits, SGPAs) are computed dynamically. This guarantees that modifying a course's credit weight immediately updates all candidate SGPAs without manual batch updates.

Chapter 26: Implementation Details

Gradely's client logic is structured around three core architectural classes:

  1. AcadexThemeManager: Controls document styling by dynamically setting the data-theme attribute on the root HTML node. It synchronizes with localStorage and attaches a listener to window.matchMedia("(prefers-color-scheme: dark)") to seamlessly track operating system appearance shifts in real-time.
  2. AcadexEngine: The central state machine. Encapsulates all data structures, navigation routing, modal dialog managers, audit logging, and view renderers.
  3. jsPDF Transcriptor: Encapsulates vector PDF compilation, drawing institutional crests, candidate details, tabular mark registers with color-coded grade badges, and official autonomous institution seals.

Core Evaluation Routine:

evaluateStudent(st) { let totalObt = 0, totalMax = 0, totalWeightedPoints = 0; let totalCredits = 0, entered = 0, failed = 0, hasInvalid = false; const details = this.state.subjects.map((sub, i) => { const val = st.k ? st.k[i] : null; if (val === "" || val === null || val === undefined) { return { entered: false, val: null, p: null, g: null, gp: null, status: "PENDING" }; } const num = Number(val); if (isNaN(num) || num < 0 || num > sub.m) { hasInvalid = true; return { entered: true, invalid: true, val: num, status: "INVALID" }; } entered++; const p = (num / sub.m) * 100; const gr = this.getGradeForPercentage(p); totalObt += num; totalMax += sub.m; totalWeightedPoints += (gr.gp * sub.c); totalCredits += sub.c; if (gr.gp === 0) failed++; return { entered: true, val: num, p, g: gr.g, gp: gr.gp, status: gr.gp === 0 ? "FAIL" : "PASS" }; }); const isComplete = (entered === this.state.subjects.length) && !hasInvalid; const aggPct = totalMax > 0 ? (totalObt / totalMax) * 100 : 0; const sgpa = (totalCredits > 0 && isComplete) ? (totalWeightedPoints / totalCredits) : null; const overallGrade = isComplete ? this.getGradeForPercentage(aggPct).g : null; const resultStatus = hasInvalid ? "INVALID" : (isComplete ? (failed > 0 ? "FAIL" : "PASS") : "PENDING"); return { details, totalObt, totalMax, aggPct, sgpa, overallGrade, resultStatus, isComplete, hasInvalid }; }

Chapter 27: Grade & SGPA Calculation Methodology

Gradely adheres strictly to the autonomous Choice-Based Credit System (CBCS) grading guidelines. The calculation pipeline proceeds through four distinct mathematical stages:

Stage 1: Percentage Calculation per Course

Percentage_i = ( Marks Scored_i / Maximum Marks_i ) × 100

Stage 2: Grade & Grade Point Mapping

Each course percentage is evaluated against the 10-point institutional ordinance scale:

Percentage Range (%) Letter Grade Grade Point (GP) Qualitative Evaluation Conferral Status
90.00 – 100.00 A+ 10 Outstanding PASS
80.00 – 89.99 A 9 Excellent PASS
70.00 – 79.99 B+ 8 Very Good PASS
60.00 – 69.99 B 7 Good PASS
50.00 – 59.99 C+ 6 Above Average PASS
45.00 – 49.99 C 5 Average PASS
40.00 – 44.99 D 4 Pass (Marginal) PASS
0.00 – 39.99 F 0 Fail (Remedial Backlog) FAIL

Stage 3: Credit-Weighted SGPA Summation

The Semester Grade Point Average is computed as the credit-weighted average of all earned grade points:

SGPA = Σ (GP_i × C_i) / Σ C_i

Where $GP_i$ represents the grade point earned in subject $i$, and $C_i$ represents the assigned credit weight of subject $i$. If a candidate fails ($GP=0$) in any registered course, their overall semester status is flagged as FAIL (Remedial Backlog).

Stage 4: Automated Cohort Ranking & Tie-Breaker

All fully evaluated students are sorted descending by SGPA. If two candidates achieve identical SGPAs, the system breaks the tie by evaluating their overall curriculum aggregate percentage:

Tie-Breaker: IF (SGPA_A == SGPA_B) THEN Rank = (AggregatePct_A > AggregatePct_B)

Chapter 29: Security Considerations

Gradely implements defense-in-depth security principles across client execution and data export:

  • CSV Formula Injection Mitigation: Malicious input starting with sensitive formula triggers (=, +, -, @, , ) are automatically prepended with a single quote (') during CSV export, neutralizing formula execution in Microsoft Excel and LibreOffice Calc.
  • Boundary Protection: Marks inputs enforce hard mathematical constraints ($0 \le x \le ext{maxMarks}$). Non-numeric characters or out-of-bounds numbers immediately prevent SGPA finalization.
  • Tamper-Evident Audit Logging: Mutations generate unalterable audit events stored in a circular chronological buffer capturing actor, action, timestamp, and target entity.
  • Client Isolation: Student users cannot inspect administrative modals, modify ordinances, or access faculty grade entry views.

Chapter 32: Experimental Results & Performance

The system was tested using a real-world demonstration cohort of 20 first-year engineering students evaluated across 7 core subjects (700 total maximum marks, 23 total credit points). Key outcomes include:

  • Cohort Size: 20 enrolled candidates (10 in `CSE-A`, 10 in `CSE-B`).
  • Evaluation Rate: 100% complete (20/20 evaluated records).
  • Qualification Outcome: 19 Qualified Candidates (95.0% pass rate) and 1 Remedial Backlog Candidate (Abhishek Soni, failed MEC101 with 32 marks).
  • Class Average Aggregate: 77.52%.
  • Top Cohort SGPA: 9.87 achieved by Class Topper Ananya Verma (93.57% aggregate).
  • Rendering Latency: Zero perceptable delay (< 15 milliseconds) when switching views or updating marks.

Chapter 33: System Limitations

While Gradely successfully satisfies all Milestone 5 project goals, several operational boundaries exist:

  • Local Storage Scope: In the standalone client model, updates made on one device are stored in that device's browser local storage. Synchronizing across disparate physical devices without manual export/import requires provisioning the included PostgreSQL/Express backend.
  • Single Semester Scope: The current active interface focuses on single-semester tabulation (SGPA). Multi-semester Cumulative Grade Point Average (CGPA) progression requires activating the backend semester progression schema.
  • Network-Independent PDF Signing: PDF transcripts utilize digital watermarking and verification hashes rather than X.509 PKI cryptographic smart-card certificates.

Chapter 34: Future Enhancements

  • Biometric & Single Sign-On (SSO): Integration with Google Workspace for Education and OAuth2 campus authentication.
  • Automated SMS & Email Broadcasts: Instant dispatch of semester scorecards to student and parent mobile numbers via Twilio / SendGrid APIs upon result publication.
  • Blockchain Transcript Verification: Anchoring published transcript cryptographic hashes to a public ledger (e.g. Polygon / Ethereum) for tamper-proof global credential verification by employers and foreign universities.
  • Mobile Native Application: Packaging the responsive web codebase into Android and iOS native builds using Capacitor or React Native.

Chapter 35: Conclusion

The Gradely – Student Grade Evaluation System (Acadex 2.0) project demonstrates that modern browser technologies, thoughtful architectural design, and strict mathematical modeling can effectively overcome the deep-seated flaws of traditional spreadsheet-based academic evaluation.

By delivering sub-millisecond calculation speeds, strict Choice-Based Credit System (CBCS) grading adherence, role-based authorization, high-fidelity PDF transcript generation, and a zero-server-cost cloud deployment on Render, Gradely presents a robust, scalable, and complete solution for autonomous engineering colleges. The system fulfills all requirements of the B.Tech First Year Project curriculum with distinction.
